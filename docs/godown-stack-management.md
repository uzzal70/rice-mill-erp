# Godown and Stack Management

## Workflow

An authorized user creates a godown under the selected company and factory, then defines one or more capacity-limited stacks within it. Stack metadata can identify the designated material, variety, crop year, batch, lot, and received date. Inventory stays ledger-driven; the master-data screen does not directly edit stock balances.

## Data model and relationships

- `Godown` belongs to one company and factory and can contain multiple stacks.
- `Stack` belongs to that same company, factory, and godown; compound foreign keys prevent cross-company or cross-factory placement.
- A stack may reference a designated company-owned `Item`. Variety, crop year, batch, lot, and received date are retained as stack-level storage metadata.
- `StockMovement` records remain the source of truth for stock. Movements reference a stack and item independently; they are not replaced by capacity or metadata fields.
- Migration `0012_stack_storage_metadata` adds optional stack metadata and an item foreign key without changing existing stock history.

## Calculations and integrity

- Occupied KG is derived from the signed stock-movement balance at the stack; available capacity is `capacityKg - onHand`.
- Occupancy percent is `onHand / capacityKg × 100`, bounded for the display. Inventory posting continues to enforce stock and capacity checks transactionally.
- Age in days is calculated from the stack's recorded `receivedAt` date. Bands are 0–30, 31–60, 61–90, and over 90 days. Missing dates are shown as unknown rather than fabricated.
- Received-date aging is stack-level, not FIFO layer aging. A stack containing multiple receipts/lots does not yet expose per-lot age; use receipt/lot-level inventory reports when that ledger support is available.
- Capacity updates cannot reduce capacity below current occupancy. Capacity must be positive; material references must be active and in the same company; received dates cannot be in the future.
- Creating or updating stack master data creates an audit event. No accounting entry is generated by location setup; stock/accounting effects remain tied to posted inventory source documents.

## API and permissions

- `GET /api/v1/godowns?companyId=...&factoryId=...` lists godowns and stacks with computed occupancy, available capacity, age, and designated material.
- `POST /api/v1/godowns` creates a scoped godown (`godowns:CREATE`); listing requires `godowns:READ`.
- `GET /api/v1/stacks?companyId=...&factoryId=...` lists stack occupancy and metadata (`stacks:READ`).
- `POST /api/v1/stacks` creates a stack (`stacks:CREATE`).
- `PATCH /api/v1/stacks/:stackId` updates stack code, capacity, and storage metadata (`stacks:UPDATE`).

All writes validate company/factory/godown relationships and return human-readable errors for duplicate codes, invalid material/date, or insufficient capacity.

## UI and verification

The bilingual Warehouse screen is scoped to the selected company and factory. It creates godowns and stacks, edits stack details, displays live capacity bars and occupied/available KG, and summarizes aging bands. Stock quantities remain based on inventory movements.

Coverage includes stack metadata creation and audit, capacity-reduction rejection, occupancy/available-capacity calculations, aging band calculation, Prisma schema validation, backend tests/build, and frontend typecheck/production build.
